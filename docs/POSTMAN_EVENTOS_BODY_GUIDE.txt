Body mínimo y completo para POST /api/v1/eventos

Regla general:
- El Authorization debe llegar en el header como: Bearer <token_del_dispositivo>
- El dispositivo se identifica por el token, no por el JSON.
- El dispositivo_id y la zona_id se obtienen del token del dispositivo y de la relación dispositivos_zonas.
- El campo id_local es obligatorio para detectar duplicados en accesos e intentos fallidos.
- Para tipo permitidos/remotos/salida: el evento se guarda en accesos.
- Para tipo denegado: el evento se guarda en intentos_fallidos.
- Para tipo alarma: el evento se guarda en alarmas y, si existe, se enlaza el último intento fallido.
- Si usuario_id viene null y tipo es permitido, el backend intenta buscar al usuario por nombre temporalmente.

Notas importantes:
- Para tipo alarma, el campo tiene_foto puede llegar en true, pero no se guarda directamente en la tabla alarmas porque esa tabla no tiene ese campo; solo se usa para el flujo de fotos si luego se integra con la copia de archivos/foto_ruta.
- El valor de score para alarma suele venir en null. Si llega un valor, no se usa como columna en alarmas; el registro se guarda en la tabla de alarmas con campos básicos y sin score.
- La validación de duplicado para alarmas no usa id_local porque alarmas no tiene esa columna; por ahora se revisa dispositivo_id + fecha exacta.
- La validación de duplicado para accesos e intentos_fallidos sí usa (dispositivo_id, id_local).
- Para salidas, usuario_id puede quedar null, y el acceso se registra con tipo_acceso = 'salida'.
